I believe the in-depth research documented in [[Technique Research Report (TRR)]]s is the path forward for detection, and I worry about how unprepared we are to detect compromises of [[Trusted Service Infrastructure (TSI)]] products. As our enterprises grow increasingly complex and interconnected, more and more management work is executed through TSI products like application deployers, CI/CD, password vaults, and workflow automation tools. These products (when SaaS-hosted) can provide initial-access vectors through compromise or exploitation, but are also trivially accessed using stolen user cookies. With that concern in mind, what would be required to write TRRs on TSI products?

I had to consider this problem while reading [MDSec's excellent report on attacking ServiceNow](https://www.mdsec.co.uk/2026/08/when-it-snows-it-pours-anatomy-of-a-servicenow-red-team/). ServiceNow started as an IT Service Management (ITSM) product, deeply integrated into operational and incident management workflows, but it has expanded to cover many more use cases (there are [dozens of products listed here](https://www.servicenow.com/products-by-category.html)). Now, with AI driving more business use cases, [ServiceNow's website says](https://www.servicenow.com/what-is-servicenow.html) that the company is striving to build "a single platform that brings together any AI, any data, and any workflow". This sounds like a TSI product that we need to secure! But how would we convert this detailed report into a TRR detection artifact?

## TRR procedure documentation

Both the MDSec report and the TRR look for a deep understanding of the risks posed by a given system, but the TRR requires a different level of coverage and thoroughness. The report points to possibilities; the TRR requires cataloging and discovering them. This maps to the (oversimplified) difference between attacker and defender discovery objectives; the attacker needs to find a path to the objective, and the defender needs to know all the terrain the attacker may need to traverse to that objective.

A TRR starts with identifying a *product* (ServiceNow) as well as a *technique* and then seeks to identify the full set of *procedures* ([[MITRE ATT&CK Procedures and Instances|see here]]) that can be used to perform the technique on that product.  For example, the MDSec report mentioned multiple methods to execute Javascript-derived Glide scripts. This maps to a specific MITRE ATT&CK® technique ([Command and Scripting Interpreter: JavaScript - T1059.007](https://attack.mitre.org/techniques/T1059/007/)) but can also be broken into the procedures identified by MDSec, including:

- Create or modify a transform (which can contain a Glide script) and arbitrarily trigger it
- Create or modify a business rule (which can contain a Glide script)
- Create a scheduled job (which can, you guessed it, contain a Glide script)
- Create a custom action within a Script Step in the Workflow Studio (yeah, it runs a script too)
- Create a script condition in `sysauto_ms_report_builder.do` and manually execute a report
- Exploit RCE vulnerabilities ([example 1](https://www.slcyber.io/research/smashing-the-servicenow-sandbox-pre-authentication-rce), [example 2](https://appomni.com/ao-labs/bodysnatcher-agentic-ai-security-vulnerability-in-servicenow/)) to run Glide scripts

We would document each of the bullet points as individual procedures in one TRR document, along with a mind-map-style Detection Data Model (DDM) that helps identify common telemetry or control paths. With the DDM in hand, we can write the minimum number of detections needed to cover the entire technique. For example, a detection that only monitors business rules will prove insufficient, but if all Glide script executions trigger a common audit log[^2], that could provide a robust monitoring source.

At this point, several issues come to the surface:

- This list of procedures for Glide script execution is almost certainly incomplete (and we do not know if the other methods will generate similar logs or artifacts)[^1].
- The audit logs may not contain enough information to determine the provenance of the script. For example, scheduled task logs usually only include metadata such as the task name, schedule, executed action, and command-line arguments. If the scheduled task calls a script, that script's content remains hidden from defenders using audit logs alone.

The solution is to accept that [[some techniques should only be detected opportunistically]]; execution-associated techniques like this one are usually included in that category. Instead of looking for all the ways attackers can achieve execution, we need to look for the _changes_ the attacker is able to achieve by executing arbitrary code. This is where the other tactics—like persistence, privilege escalation, discovery, and lateral movement—come in.

To be clear, if we **can** build detections for execution, they are useful, but they should be treated as opportunistic rather than complete or comprehensive. Defenders should deploy execution detections where possible, since the techniques and detections are constantly evolving in a cat-and-mouse game with vendors like ServiceNow. To get ahead, defenders must prioritize their efforts around "chokepoint" techniques.

## What techniques should we focus on?

The inventory retains execution-related techniques for completeness, but these techniques usually remain opportunistic rather than serving as comprehensive detection objectives. What techniques are worth further attention? Here, we encounter a new roadblock; ATT&CK does not currently have good technique coverage for TSI ([[MITRE ATT&CK® is not flat]]), let alone the specific platform—enterprise automation / Digital Process Management (DPM)—that includes ServiceNow as a product[^3]. Not only do we have to identify procedures, but we have to identify the techniques!

The (marginally) good news is that many of these techniques should be common across the DPM platform[^4], so once we do this work for one DPM product, we should be able to use it as a basis for other products in the platform. Additionally, ATT&CK is broad enough that it contains many (high-level) techniques that we can adapt for this purpose—I only found one case where a key technique was missing from the inventory (*Clear Application Logs* as a child of T1685).

## High-value techniques

Technically, a TRR could be written for any of the techniques listed above, but a few techniques look especially promising:

- Defense Impairment techniques - hiding your tracks is fine unless defenders are watching for that!
- Discovery—find sensitive integrations
- Privilege escalation techniques—this might be detectable by comparing data from two points in time.
- Persistence - baselining appropriate usage locations for service accounts (ideally, lock these down with policies!)

Once we pick a specific technique, we will repeat the process described above. For example, for the proposed [T1685 — Disable or Modify Tools](https://attack.mitre.org/techniques/T1685/) subtechnique for the DPM platform, _Clear ServiceNow login history_, we would want to identify the procedures that could be used to execute that technique. This would start by understanding the documentation and features available for it—including ==UI history deletion== and ==API history deletion==—and would also require creative "red teaming" to consider other ways to delete the history. What about ==directly deleting or dropping history records from the underlying table==[^5]? Separately, a test of ==disabling the audit service and immediately re-enabling it== would investigate the [T1685.002 — Disable or Modify Cloud Log](https://attack.mitre.org/techniques/T1685/002/) path, which the report does not demonstrate.

While identifying procedures, we would also build our Detection Data Model: part process flow and part telemetry/control inventory. By drawing out the flow of the specific procedures, we might discover that UI and API history deletion actually use the same endpoint and telemetry and can be consolidated into a single procedure. We'll also want to build a simulation environment if possible to validate our research; ServiceNow [appears to offer a developer instance](https://www.reco.ai/hub/servicenow-developer-instance-setup-management) that would be perfect for this task. We would test each procedure, ensure it generates the expected telemetry, and correct any errors in our TRR/DDM. Along the way, we'll also log architectural information about ServiceNow that is key context for red teamers, incident responders, and detection engineers who may work with this data later. For example, sample log lines could be a useful contribution.

## Reap the benefits

After the TRR is written, it becomes immediately useful for the groups described above:

- Red teams don't have to rediscover key features of the products they are attempting to test
- Incident responders and threat hunters have a much better sense of where to investigate for suspicious activity
- Detection engineers know what [[Turning the TIDE with Test-Initiated Detection Engineering|validation tests]] and detection rules they need to build to secure the ServiceNow product

Here's the benefit of TRRs: instead of this research happening in parallel across dozens of security organizations, every team can benefit from the TRR's shared findings and collectively document a **different** part of the security paradigm. Hopefully, this post gave you a better sense of the differences between TRRs and red team finding reports and an idea of how to leverage the latter to generate the former. Please let me know if you're interested in trying TRR writing yourself.
